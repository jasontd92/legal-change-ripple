  These are the places where I'd push back or propose something different:

  1. The "formatting only" check should be code, not an LLM. Strip whitespace,
  HTML markup and encoding differences, then diff what's left. Anything that
  survives goes to step 1. In legal text, one word ("shall"→"may", "and"→"or", a
  date) can change the meaning. An LLM shouldn't be allowed to wave those
  through as typos.

  2. Keep the vault out of the applicability step. Applicability asks whether
  the change applies to the company, so decide it from the profile. If the model
  sees a file list at this point, you get the worst recall failure in the
  system: "no filenames mention tariffs, so this doesn't apply." The contract
  that matters is Acme_MSA_2023.pdf, and the tariff reaches it through the
  definition of "Duties." Also, when the custom prompt narrows the focus, that's
  a fine reason to exit, but log it as a dismissal with a reason so the
  coverage statement stays honest.

  3. Build a short summary of each stack once, when documents are uploaded. This
  is my main alternative to both file names and a knowledge graph. For each
  stack, extract:
  - the parties, and whether we're buying or selling
  - the contract type and governing law
  - each file's role (MSA, PO, amendment, incorporated web page)
  - which key clause types are present (CUAD's 41 categories are a ready-made
    list)

  It doesn't depend on any particular change, so it's cached. It's basically GC
  AI's Vault extracted columns. Scoping then reasons over these summaries.
  Scoping is also the most dangerous decision in the pipeline, because a stack
  it excludes is a miss nothing downstream can catch. So default to including
  stacks, give a reason for every exclusion, and evaluate scope recall on its
  own. That's also why I'd keep steps 3 and 4 separate. The reason isn't cost:
  scoping produces its own user-facing record and needs its own score.

  4. Reframe step 4 from "stale clauses" to "the rights, obligations and 
  exposures this change creates." "Stale" is amendment thinking, which belongs
  to step 7. The most valuable findings often aren't stale clauses at all:
  - a pass-through right you can exercise
  - a notice window that started running on the effective date
  - a protective clause that's missing

  If the subagent returns only citations, the orchestrator has to re-read
  contracts to rank them, which breaks context isolation. The subagent's output
  has to carry the facts: who bears the cost, what the exposure is based on, the
  deadline, and whether the right is lost if the deadline passes.

  5. Your scoring system and the "no LLM scores" rule can both hold. The LLM
  extracts facts and picks labels from a fixed list; code computes the rank.
  That's already allowed under "arithmetic on contract facts." My case for how a
  GC ranks:
  - Forfeitable deadlines first. A missed notice window is permanent; a large
    exposure with no clock can wait a week.
  - Then dollars, measured against the GC's stated threshold.
  - Then direction: is the company exposed, or holding a chance to recover
    money?
  - Then legal certainty: effective law beats a proposed or stayed rule.
  - "Needs review" items go high enough to be seen.
  - Clerical updates go last, as one batch.

  I'd rank with sort keys in a fixed order, not a weighted sum. Every position
  can then be explained in one sentence ("#1: notice window closes in 9 days").
  When a rank changes between runs, you can trace it to the specific fact that
  changed, and that's the consistency anchor you asked for.

  6. On your step 6 question: yes, step 5 needs part of it. Step 5 needs the
  type of response (send notice, exercise pass-through, seek a refund, update a
  template, monitor), not the full plan. "Notice by Oct 12" ranks very
  differently from "fix at renewal." So each finding gets a response type.

  7. Cross-stack effects fit naturally in step 5. The orchestrator is the only
  component that sees findings from every stack. It can link "supplier can pass
  the tariff through" with "customer contract is fixed-price." How far to take
  that depends on the L1/L2 scope decision that's still open.

  How the categorical framework works

  Every judged dimension follows the same three rules:
  - A few categories, each with a one-line test. The tests are written into the
    prompt so the choice is about meaning.
  - An explicit "undeterminable" category that names the missing fact. For
    example: "notice period depends on a PO we don't have." This is how a
    conservative "needs review" gets into the data without a confidence number.
  - The LLM never sees the ordering. It classifies; code decides which category
    outranks which. The ranking policy then lives in one place you can review
    and change without re-running a model.

  Here's how each dimension works out:
  - Urgency: forfeitable clock running · obligation clock running · clock
    pending on a future event · no clock · undeterminable. When a date exists,
    code computes days remaining.
  - Materiality: material / not material / undeterminable. It's material if any
    concrete test fires:
    - it shifts a recurring cost
    - it creates, removes or changes the value of a right
    - it creates a compliance or breach risk
    - it starts a clock
    - it meets the GC's threshold

    The threshold is just one more test, and it only applies when the GC gave
    one. Without it, the other tests still decide, so a missing dollar figure
    doesn't break anything.
  - Legal status: a factual state, not a spectrum: in force · effective later ·
    in force but challenged · stayed · proposed · vacated · undeterminable. It
    sits on the change record from stage 1, not on each finding, because it
    describes the law, not the contract.
  - Direction: exposure / recovery / both / neutral. I'd use it to group the
    report, not to rank it. A GC reads "what we owe" and "what we can recover"
    as two separate to-do lists with different audiences (finance versus
    counterparties), and neither is inherently more urgent.

  The ranker then sorts in this order:
  1. Legal status as a gate. If the change is stayed, proposed or vacated, all
     its findings go into a "watch" band.
  2. Materiality.
  3. Urgency category.
  4. Days remaining, then dollars if known.

  Clearing up my earlier question: I was mixing two things that run at different
  times.
  - Stack summary: built once per stack when documents are uploaded, before any
    change arrives. It exists only so stage 3 (scoping) can decide which stacks
    to investigate without reading full documents.
  - Subagent: the stage-4 analyst, one per in-scope stack, launched after
    scoping.

  The question was about what happens when a stage-4 subagent, reading its own
  stack, finds a pointer to something outside it. An example: "pricing tracks
  the rates in our supply agreement with X." Should it look at stack X to
  resolve that?

  My recommendation is no. The subagent records the pointer in a
  cross_references field and moves on. The stage-5 orchestrator resolves those
  pointers, since it's the only component that sees every stack. It can also
  send a follow-up question to stack X's subagent. That keeps each subagent
  isolated and gives cross-stack effects (your L2) a single place to happen,
  which makes them easy to evaluate and to cut from scope if needed.

  Still open: who builds the stack summaries (an agent at upload, or
  hand-written for the eval corpus), and the default window for "urgent" when
  the GC doesn't give one. I'd suggest 30 days.

  - eve is built on AI SDK plus Vercel's Workflow SDK, with a convention where
    an agent is a directory of files. Its pieces map almost one-to-one onto this
    design:
    - the durable session is the orchestrator thread
    - a declared subagent returning structured output is the per-stack analyst
      returning its finding
    - skills can hold the legal playbooks
    - schedules cover the monitoring cron

    It runs locally without Vercel, storing workflow state on disk.
  - pi is an excellent minimal agent loop, but it's interactive and
    coding-focused, with no durability or subagents by design. You'd spend your
    hours building the exact things this project is meant to show off before
    starting on the legal problem.

  I'd go with eve. Since it's AI SDK underneath, your familiarity carries over,
  and switching models for the comparison is a one-line config change.

  Temporal: don't add it on top of eve, because eve already gives you durable
  execution and you'd end up with two layers doing the same job. Temporal is the
  right choice if you use plain AI SDK. It has a plugin that wraps each model
  call so it gets retried and recovered, and it's more mature, but it needs a
  Temporal server and some discipline about which code may call out to the
  network. So the real choice is eve versus AI SDK plus Temporal, and Temporal
  is the fallback if eve's beta causes trouble.

  How eve handles long-running, recoverable work. I read the docs and ran a
  crash test locally.

  The design:
  - Each eve session runs as a durable workflow. A "step" is one model call plus
    the tool calls that follow it, and that's the checkpoint unit.
  - State isn't SQLite. It's an append-only event log. On a local setup that's
    one JSON file per event under .eve/.workflow-data/, recording that a step
    was created, started or completed.
  - Recovery works by replaying that log. Finished steps return their recorded
    results instead of running again, and a step that was interrupted runs again
    from scratch.
  - A queue drives execution. Locally it lives in memory; on Vercel it's Vercel
    Queues; self-hosted, it's Postgres.

  The test used a fake model scripted to call a tool three times, with each call
  taking 6 seconds. I killed every process with kill -9 during the third call.

  The ground rules:
  - Unit evals feed each stage the correct answer from the stage before it
    (called teacher forcing). An error can then be pinned on the stage under
    test rather than inherited. Integration evals use the real upstream output
    to show how errors compound.
  - Two pass/fail checks come before any scoring: the output matches its
    expected format, and every quoted citation appears word for word in the
    source.
  - Anything that filters or flags is scored with F2, which weights recall twice
    as heavily as precision. Precision and false-alarm rate sit next to it, so
    a flood of alarms still shows up.
  - Some category mix-ups cost more than others, so each category set gets a
    small table of how bad each confusion is.
  - Every scenario runs 3 times.
  - Always measured: cost, tokens (orchestrator vs subagents), tool calls,
    retries, and time per stage. Time is recorded but not scored.

  Unit evals, one headline metric each:

  Integration evals (details in the doc):
  - End to end: the headline product number. Did the findings that matter reach
    the report, labelled material?
  - Funnel attribution: for every gold finding that gets missed, which stage
    lost it. This is the main tool for deciding which lever to pull next.
  - Handoff fidelity: full findings vs summaries passed to the orchestrator.
  - Ranking approach comparison: labels plus code sort, the agent ranking
    freely, or code sort with the agent reordering ties; also LLM labels vs Jev
    labels.
  - Consistency: how much repeated runs agree.
  - Robustness: cosmetic-only or duplicate triggers, unparseable files, injected
    tool errors, and killing and restarting mid-run.
  - Generalization: the performance gap between trigger types on the same
    corpus.
  - Model comparison: quality against cost for each model setup.
  - Informal comparison with the GC AI trial account.

  For the headline, I'd report a short scorecard rather than one combined
  number, because a single number hides which part moved. The scorecard:
  citations correct (must be 100%), recall of material findings, false-alarm
  rate, ranking accuracy, consistency, and cost per run.

⏺ I've rewritten eval-design.md as revision 2 and kept your edit that defers the
  exclusion-reason check. It doesn't touch the documents themselves.

  1. Gap analysis: where the agent could fail without any eval noticing

  The pattern: most undetected failures come from output that looks faithful but
  isn't what it claims to be. The word-for-word citation check passes on all of
  these:
  - Quoting text that no longer applies. The agent quotes a base-contract clause
    that an amendment replaced, or reads the current version of supplier terms
    when the PO points to an older dated version. The corpus has both.
  - Treating expired or superseded documents as live.
  - Right answer, wrong reason. The agent cites the right clause but skips a
    required step in the reasoning, such as an override in a child document. We
    only scored the outcome.
  - Quotes cut off before an exception ("…except as provided in…").
  - Claiming to have read what it didn't. The read tool can silently truncate a
    long document, or a tool-call budget can run out. The coverage statement was
    self-reported and never checked.
  - "This protection is missing" when a search simply failed to find it.
  - Reading the template and assuming every signed copy matches. The corpus has
    about 20 signed copies that vary by state, role and date.
  - The report dropping or merging findings, or leaving a cross-reference or 
    change item unresolved. We scored what appeared in the report, not what
    vanished.
  - A wrong "not material" label. That hides the finding from the default view,
    and it was averaged into overall label accuracy.
  - No eval at all covered the custom prompt, sensitivity to the company
    profile, scale, or dependence on file names and order.

  There are two main additions:
  - 12 automated checks that run on every run, with no AI cost. They cover:
    quotes appear within the cited section; no quote is cut off before an
    exception (a text check); no finding relies on superseded text or expired
    documents; claimed reads are verified against the tool log, including how
    much of each file was actually returned; every "missing clause" claim lists
    where it searched; no finding disappears between subagent and report; and
    every cross-reference and change item is accounted for.
  - 7 "change one input, predict the output" evals. Because they only predict
    how the output should change, they need no new answer key. For example:
    - shift the as-of date, and deadlines should change as predicted
    - swap the company profile, and the company-level check should flip
    - add a focus or a dollar threshold to the custom prompt
    - scale the corpus from 240 to 300 documents with extra noise
    - rename or reorder files
    - delete one clause the finding depends on, and the finding must change

    That last one is the strongest single test that the agent is actually
    reading its sources.

  2. Metric analysis

  - Now deterministic: almost everything. Every planted clause has an ID and
    exact text, so a finding matches the answer key when it's in the same stack,
    addresses the same change item, and its quote overlaps a required passage.
    That also replaces the LLM check for "does the citation support the claim":
    citing the required passage is the support. "Who it applies to" becomes
    structured fields, compared as sets.
  - Now binary: every metric counts yes/no units. Stage 4's headline counts a
    finding only if it cites every required step in the chain. Ranking uses
    three yes/no checks:
    - every top-tier item sits above every bottom-tier item
    - every top-tier item appears in the top N
    - no top-tier item is hidden as not material

    Instead of weighting each category mix-up by severity, the dangerous mix-ups
    are counted separately with a target of zero: false exits, relevant stacks
    scoped out, material findings labelled not material, and missed deadlines
    where a right would be lost.
  - Redundant, now merged:
    - A stack's overall verdict is derived from its findings.
    - Decoy and missing-clause detection are slices of the finding metrics.
    - The report-quality rubric is replaced by the automated checks.
    - End-to-end, funnel attribution, consistency, generalization and the model
      comparison are all analyses of the same end-to-end runs, so they add no AI
      cost.
  - LLM judge usage: down to two optional yes/no checks. One asks, per report
    item, whether the rationale contradicts its labels (batched as one call per
    report). The other is a fallback for matching findings, only if the
    deterministic rule turns out too brittle. Each would use a different model
    family from the agent and be checked against about 30 hand labels. Nothing
    in the headline metrics depends on a judge.
  - Getting a clear signal from a small eval set:
    - Compare configs item by item, counting what got fixed and what broke, with
      a standard significance test (McNemar's) instead of comparing two
      percentages.
    - An item counts as reliably correct only if it passes all 3 runs. This
      folds consistency into accuracy.
    - Break results out by slice, and report raw counts when a slice has fewer
      than about 30 items.
    - Freeze the held-out split before the first round of prompt changes.
    - Cache subagent results by content hash, so repeat runs only pay for what
      changed. Subagents are where most of the cost goes.

  What this means for the corpus brief: the answer key needs to anchor
  everything to specific source passages:
  - the passages a correct finding must cite, and which passages are superseded
  - deadlines as structured rules
  - who a change applies to, as structured fields
  - priority tiers written from judgement, not generated by our ranking rules

  Most of this falls out of the collection plan's planted-feature list, each
  document's status, and the parent links between documents. The required
  reasoning steps per finding, the labels, the cross-stack links and the
  priority tiers still have to be written by hand.

  One open question affects scope: does the orchestrator read the historical
  findings log? If it does, the "same trigger twice" and "trigger that reverses
  an earlier one" robustness cases become testable. If not, they're out of
  scope.
