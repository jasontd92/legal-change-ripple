⏺ I'd skip the sidebar table of contents. The page only has 3–4 sections, so a
  sidebar takes width away from the finding rows and still doesn't tell you what
  needs attention. I'd put one summary line at the top that also works as 
  navigation, and limit how many rows each section shows so the whole page fits
  in a couple of screens.

  What I'm seeing in ReportView.tsx

  - Grouping: findings are grouped by direction (exposure / recovery / both /
    neutral) in GROUP_ORDER. At 7am, though, a GC's first question is "what
    needs me before it's too late?" That's the deadline, which today only shows
    up as a chip or a colored row edge inside each group.
  - Filters come first: the category and date filters sit above everything else.
    That puts controls in front of content before you know if you need them.
  - Hidden sections: "Not material" and "What was reviewed" are folded away at
    the bottom of a list with no length limit. You can only find them by
    scrolling.

  Recommendation

  1. A summary line at the top. One line of text, not a row of dashboard tiles:

  Daily review · Oct 1
  2 need action  ·  5 to watch  ·  12 set aside  ·  40 changes reviewed

  Each count is a link that jumps to or filters that section. The line does two
  jobs at once:
  - It answers "is today bad?" in about a second.
  - It shows everything on the page, including the two folded sections, so you
    don't have to scroll to find out they exist.

  "40 changes reviewed" also reassures you that nothing was skipped, which
  matters to a GC.

  2. Group by what you need to do, and show direction as a label.
  - Needs action: the deadline is running (clock.hot / tone act). These rows
    show open.
  - Watch: the finding matters but has no deadline or an unclear one.
  - Set aside / Reviewed: these stay folded, as they are now.

  Exposure vs. recovery becomes a small label on each row. This mostly reuses
  fields you already compute (clockChip, materiality). It's a change to how rows
  are grouped, not a new data model.

  3. Limit each section. Show the top 5 by rank, then a "Show 12 more" row. That
  keeps the page short enough to reach the bottom sections, and rank order
  already puts the right rows at the top.

  4. Hide the filters until they're needed. Clicking a count in the summary line
  already filters. Put category and date behind a small "Filter" control, or
  only show them once a section has more than about 10 rows.

  5. Make the empty state the headline. On a quiet day, show "Nothing needs you
  today. 40 changes reviewed, 12 set aside." That's the best possible morning
  report, so say it plainly and don't show empty sections.

  This approach removes things rather than adding them. The new pieces are one
  line of text and a "show more" row. The filter bar moves out of view, and the
  empty direction sections go away.

❯ I ,ike #4 for a different reason - the page is still dense in terms of        
  labels, options, and sections. Looking to deeply simplify/make context        
  "progressive" - meaning, the only thing suyrfaced to a user is what they need 
  to know in that very moment. And guiding them to what they need to know       
  next. How else can this principle be incorporated to this page? I like the    
  premise of a top line "status" bar - but the page feels filled with           
  catgeories and badges and ways to filter already. Thoughts on how to improve  
  the page layout hilsitically?                                                 

⏺ The page is dense because every layer of information shows up at once. Each
  row currently has a rank, document name, headline, deadline label,
  legal-status label, action verb, dollar amount and urgent marker. Above the
  rows sit two filter groups, and section headers carry counts. To make the page
  progressive, give each layer one question to answer. Each layer then ends by
  pointing to the next one, instead of using headers and badges.

  Four layers, one question each

  Layer 0: "Is today bad?" Replace the status bar with one plain sentence:

  ▎ Two things need you this week.

  A sentence reads faster than four counters, and it doesn't add any badges.

  Layer 1: "What do I do?" Each row is one line saying the action and the
  deadline:

  ▎ Send non-renewal notice to Valley Medical · by Nov 1
  ▎ Claim the $2,400 duty refund from Keystone

  The only styled element is the deadline, and it appears only when there is
  one. The other signals either move into the sentence or go away:
  - Rank number: the order of the list already shows rank.
  - Category and direction: these become the verb. "Claim a refund" already
    tells you it's a recovery.
  - Document name: it goes inside the sentence.
  - Dollar amount: it moves to layer 2, unless the amount is the reason for the
    action.

  Layer 2: "Why?" Clicking a row shows 1–2 sentences explaining why (the
  agentNote you already have) and nothing else. That's enough to decide whether
  you agree.

  Layer 3: "Show me." A "See the language" link below the explanation opens the
  side-by-side comparison of your clause against the change, plus the diff. The
  top-level "See what changed" button moves down here too, since the diff is
  evidence and not something you need first.

  Point to the next thing instead of adding more sections

  Take out the section headers. Each part ends with a sentence that leads into
  the next one:

  Two things need you this week.

    Send non-renewal notice to Valley Medical        by Nov 1
    Claim the $2,400 duty refund from Keystone

  That's everything urgent. 5 more are worth watching  →

  Reviewed 40 changes. 12 didn't affect you  →  see why

  The watch list and the set-aside items stay folded until you ask for them. The
  last line gives you confidence that nothing was missed, with the details one
  click away.

  Take the filters out

  If the page opens with filters, you're doing the sorting that the report
  should have done for you. For a morning report, the ranking is the filter. If
  a day produces so many items that you'd want to filter them, fix the ranking
  and grouping rather than asking you to sort. I'd remove both filter groups
  completely rather than hide them.

  One cost to plan for

  Layer 1 needs a short action sentence per finding. Today what holds the
  finding itself, not the action to take. You can either have the agent write a
  headline field (the verb, the counterparty and the object), or build it from
  response_type + the document + when. Having the agent write it will read much
  better, and it's one extra field in the output schema.

  What goes away

  - Filter bar and the section headers with counts
  - Rank numbers
  - Category, direction and legal-status labels (legal status shows up only when
    a change isn't in force yet, written into the sentence)
  - The top-level diff button

  What gets added is three connecting sentences.

  Want me to build this in ReportView.tsx against the #/preview sample? I'd
  start by building the action sentence from fields you already have, so we can
  see the layout before changing the agent's output.

  Root cause, reproduced in 3 of 3 runs
  - Oversized tool calls. Stage 1 asked the model to write about 10k characters
    in a single commit_change_record call: an array of nested objects, each
    holding a long summary, a repeated file path, and a quote copied
    word-for-word from the source text.
  - The model mangled that shape. Some of the models we run (GLM is the one
    observed) sometimes send the whole array as a string, with broken escaping,
    or drop required fields partway through the list.
  - The failures were invisible. The SDK rejected these calls before our code
    saw them, so they never reached the trace, and the saved transcript kept
    only the final step.
  - The harness trusted the first valid call. So when the model sent a debugging
    probe to find out what was wrong, that probe became the run's change
    record.

  Stage 4 (commit_finding) had the same pattern. The TR-13 run logged 16 invalid
  calls, and the same stacks failed again when I re-ran them before the fix.

  The fix: the model points at text, and the code does the rest
  - Line numbers instead of copied text. The snapshot and every read result are
    shown with line numbers. The model cites "lines": "209-214" and the harness
    reads the text itself, so there's nothing to escape and nothing to retype.
  - One small, flat call per item. Stage 1 uses record_change for each item,
    then finish_change_record. Stage 4 uses record_finding and
