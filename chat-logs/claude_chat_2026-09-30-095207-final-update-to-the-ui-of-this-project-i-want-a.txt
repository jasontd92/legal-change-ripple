  Your question: the incorporates junction today

  It isn't stored anywhere. There's no JSON file for it. §4 says "an edge list
  beside the manifest," but in practice buildIncorporates (src/incorporates.ts)
  rebuilds it in memory at the start of every run (src/pipeline.ts:52, :579). It
  scans every document's text for another document's published_url and picks
  the version from the pin wording.

  For a stage-4 subagent it's still very accessible, because it arrives with the
  task rather than having to be looked up:

  1. In the brief: each row whose source is in the family is written into the
     prompt as target | section | pin | quote (src/agents.ts:430,
     src/prompts.ts:123). The subagent sees the naming clause and the pin before
     it makes a single tool call.
  2. In the reading set: readingSet (src/stacks.ts:106) adds each target file to
     the files the subagent may open, so grep and read reach it. Anything past
     one hop is refused by the tool.
  3. In the instructions: the prompt tells it to follow one hop and treat pins
     as binding (prompts.ts:13).

  Where it falls short:

  - The reverse lookup isn't built. §4 says that when the trigger URL is itself
    an incorporated document, stage 3 should treat every family pointing at it
    as relevant. Nothing in the code runs that query. Those stacks only come in
    through the default of including every stack.
  - You can't inspect it. Because the edges are never written out, you can't see
    which rows a run used. And a change to how URLs are matched would silently
    change the rows between runs.
  - The subagent can't query it. It gets only its own family's rows and has no
    way to ask "who else names this target?" That matches the design ("do not
    walk to other sources"), so it's a limit rather than a bug.

  The cheap fix for the second point is to write edges to
  runs/<id>/incorporates.json next to scope_trace.json. It's a one-line change,
  and it also gives the stage-3 reverse lookup something concrete to read from
  later.

❯ tradeoffs of packed grid vs ELK?                                              

⏺ For this corpus the packed grid is the better fit. ELK starts to earn its
  extra 470 KB only if many more links between clusters get added.

  Fit to this graph
  Packed grid (React Flow + our own layout): Good. Most clusters have no links,
  so a tidy grid of cards inside each folder panel is what you'd draw by hand
  anyway.
  ELK (React Flow + elkjs): Mixed. Its main algorithm (layered) sorts nodes by
  their links. Unlinked nodes get stacked in tall single columns, so folder
  boxes come out long and thin.
  ────────────────────────────────────────
  Folder nesting
  Packed grid (React Flow + our own layout): Easy. Folder panels are plain boxes

  and the cards are placed inside them in rows.
  ELK (React Flow + elkjs): ELK can pack each folder separately with its
  rectpacking mode. Its layered mode can route links across folder borders, but
   only if the whole graph uses layered. You can't combine the two, so you pick
   tidy folders or routed links.
  ────────────────────────────────────────
  Link drawing
  Packed grid (React Flow + our own layout): React Flow draws the 16 links as
  curves. A few will pass over other cards. They read fine at this count but
  get messy past a few dozen.
  ELK (React Flow + elkjs): Right-angle links that go around cards, in layered
  mode only. This is ELK's real advantage.
  ────────────────────────────────────────
  Bundle size
  Packed grid (React Flow + our own layout): About 60 KB, loaded only on the map

  page.
  ELK (React Flow + elkjs): About 530 KB, also loaded only on that page. That's
  negligible on localhost but noticeable on a slow connection if this is ever
  deployed.
  ────────────────────────────────────────
  Control and tuning
  Packed grid (React Flow + our own layout): About 60 lines we own. Folder
  order,
  card size and colours for reviewed vs set aside are simple edits.
  ELK (React Flow + elkjs): Dozens of string settings (elk.algorithm,
  elk.spacing.*, hierarchyHandling…). Powerful, but tuning is trial and error.
  ────────────────────────────────────────
  Stability
  Packed grid (React Flow + our own layout): Deterministic. A new file only adds

  a card, and nothing else moves.
  ELK (React Flow + elkjs): Also deterministic, but adding one link can
  reshuffle
  the whole layered layout.
  ────────────────────────────────────────
  Speed
  Packed grid (React Flow + our own layout): Instant.
  ELK (React Flow + elkjs): Under 100 ms for 131 nodes, run in the background,
  so
  fine either way.
  ────────────────────────────────────────
  Growth
  Packed grid (React Flow + our own layout): Weakens as links multiply.
  ELK (React Flow + elkjs): Improves as links multiply.

  Where each wins. The design doc plans to show more links between clusters
  later: most-favored-customer, flow-down, pass-through, additional insured and
  same-party links (§3). If those end up on the map, the graph becomes properly
  connected and ELK's layered layout with routed links is worth its size. At
  today's 16 links it isn't.

  My recommendation: build the packed grid now. The layout is one function that
  takes the clusters and returns positions, so switching to ELK later means
  replacing that function. The rendering, tooltips and page stay the same.
